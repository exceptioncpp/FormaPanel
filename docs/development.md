## Первая рабочая итерация

1. Открыть Studio Code Server из HA и папку
   `/config/esphome/formapanel-rh01`. Это полный Git checkout.
2. Для новой комнатной функции выбрать `living` или `bedroom`. Оба device/host
   entry используют один room profile. RH-01 — фиксированный визуальный эталон.
3. Менять общую композицию в `firmware/esphome/packages/rh01-ui.yaml`,
   общую info-страницу в `packages/info-page.yaml`, комнатные demo-значения
   в `profiles/living.yaml` или `bedroom.yaml`. Сохранить файл.
4. В FormaPanel Workshop выбрать тот же профиль и нажать «Обновить предпросмотр».
   Кадры и журнал появятся автоматически после запуска задания. Save сам
   сборку не запускает. Простой layout edit в проверенной среде занял 7.88 с.
5. При добавлении страницы также включить её в нужный profile и добавить
   `page.show`/snapshot в host capture-сценарий. Автоматического обхода нет.
6. После визуального review выполнить «Проверить» и «Собрать прошивку».
   Скачать Factory/OTA, затем отдельно выполнить аппаратную приёмку/установку.
7. Передавать принятые изменения через Git. Просматривать diff, включать
   новые source-файлы и исходник visual editor, если он использован.

Редактор и сборщик читают одни физические файлы. Не нужно экспортировать
весь проект из IDE в другой формат. При visual authoring допускается
экспорт одного generated UI-фрагмента с постоянными ID; ручные bindings
хранятся отдельно. Подробный пример mock → HA → native → OTA есть в методологии.

## Границы реализованного

- Есть основной RH-01, living/bedroom demo, общий info, настоящие LVGL PNG,
  ESP32 сборка, encrypted API/OTA и диагностические сущности устройства.
- Бытовые HA bindings, mock/HA adapters, SDL/noVNC и автоматическая сборка
  после Save пока не внедрены. Визуальные редакторы не открывают наш checkout
  как полностью совместимый многофайловый проект без подготовки UI-фрагмента.
- Git remote настроен; текущие изменения не были автоматически commit/push.
  Для восстановления нужны сохранённый working tree/commit и private secrets.
- Текущий GitHub workflow проверяет assets/Python; firmware/native CI отсутствует.
- На Windows не устанавливаются тяжёлые SDK. Визуальный прототип испытан
  владельцем; подробные touch/память/reconnect/HA/OTA протоколы этим отзывом
  не подтверждены и остаются отдельными проверками следующего этапа.

## Как читать историю

Исходники и действующие руководства отражают текущую реализацию. Датированные
validation reports фиксируют конкретные проверки, а research/планы отдельно
содержат кандидатов и невыполненные шаги. При расхождении старого proposal
с этими руководствами использовать актуальный runbook и проверять факт по коду.
